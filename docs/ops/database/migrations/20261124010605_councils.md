Councils as a tenant kind (#5933, plan on #5833): the council columns on `chapters` (`council_type`, `council_school_id`, `council_verified_at`, `council_verified_by`, `recruitment_model`), the `chapters_council_fields_kind` check, one council of a type per school (`chapters_one_council_per_type`), and `custom_access_token_hook` defaulting the claim to chapter-kind memberships only.

## Promotion

- **Purpose**: a council is a `chapters` row with `kind = 'council'` and its own type, recruitment model, school and the `council` archetype marker; a chapter carries none of them, and the database refuses a row that mixes the two. A school has at most one council of each type but `other`. The token hook still honours a tenant the person chose, of any kind, but its default is their one chapter, never a council, so a shipped phone (which sends the claim to chapter routes) never lands in a council by default. The hook now reads `chapters`, so `supabase_auth_admin` gets a read-only grant and the `auth_admin_can_read_chapters` policy, as it has on `users` and `members`.
- **Checks**:
  - `select count(*) from chapters where kind = 'chapter' and (council_type is not null or recruitment_model is not null or council_school_id is not null);` returns 0.
  - `select convalidated from pg_constraint where conname = 'chapters_council_fields_kind';` returns true.
  - `select indexdef from pg_indexes where indexname = 'chapters_one_council_per_type';` shows the partial unique index.
  - `select proconfig from pg_proc where proname = 'custom_access_token_hook';` shows `search_path=public, pg_temp`.
  - `select policyname from pg_policies where tablename = 'chapters';` includes `auth_admin_can_read_chapters`.
  - Sign in as a member of one chapter: the access token still carries that chapter's `active_chapter_id`.
- **Promoter notes**: writes no data. Promote before the API from #5933, which selects the new columns (`GET /v1/council`, the member view's `council_type`). The other order is safe: the old API reads none of them. The token hook change applies to tokens issued after the promotion; nothing needs a re-login.

## Rollback

Rarely worth it, and only together with reverting the API from #5933. Delete any council rows first (they fail nothing but would be left with no type), then a forward migration drops the index, constraint and columns, drops the `chapters` policy and grant, and restores `custom_access_token_hook` from 20260802120000 ([playbook](../../db-rollback-playbook.md#decision-matrix)).

```sql
drop policy if exists "auth_admin_can_read_chapters" on public.chapters;
revoke select on table public.chapters from supabase_auth_admin;
drop index if exists public.chapters_one_council_per_type;
drop index if exists public.idx_chapters_council_school_id;
drop index if exists public.idx_chapters_council_verified_by;
alter table public.chapters drop constraint if exists chapters_council_fields_kind;
alter table public.chapters
  drop column if exists recruitment_model,
  drop column if exists council_verified_by,
  drop column if exists council_verified_at,
  drop column if exists council_school_id,
  drop column if exists council_type;
-- Then re-run the `create or replace function public.custom_access_token_hook`
-- block from 20260802120000_active_chapter_jwt_claim.sql, adding
-- `set search_path = public, pg_temp`.
```
