Adds logged contacts, a prospect's owner, follow-ups and the stale-days setting to the recruitment pipeline, and clears a deleted member's ownership and follow-ups (#5934).

## Promotion

- **Purpose**: `rush_candidates` gains six nullable columns (`owner_id`, `last_contact_on`, `last_contact_by`, `follow_up_on`, `follow_up_note`, `follow_up_user_id`) and two partial indexes. Two new tables, `rush_candidate_contacts` and `rush_settings`, each with RLS on and no policies, are read only by the API's service-role client. The dispatch log's `entity_type` and `threshold` checks widen to take `RUSH_CANDIDATE` with `FOLLOW_UP` and `STALE`, for the two new morning sweeps. `anonymize_user` is redefined in full with two added updates. Writes no data.
- **Checks**: `select count(*) from rush_candidates where owner_id is not null or follow_up_on is not null;` returns 0 right after the push. `select count(*) from rush_settings;` returns 0. `select prosrc like '%set owner_id = null where owner_id = p_user_id%' from pg_proc where proname = 'anonymize_user';` returns true.
- **Promoter notes**: push before the API that reads it. The pipeline read selects the new columns, so an API ahead of this migration fails the whole Recruitment page, and its sweeps fail the dispatch claim. Older APIs ignore the new columns. Needs `20261123215153_rush_pipeline.sql` first, for the `(id, chapter_id)` key the contacts table points at.

## Rollback

Worth reverting only if the new columns or tables themselves cause trouble. Revert the API first, because the pipeline read selects every column here. Forward migration:

Redefine `anonymize_user` first, in the same migration and before the drops: the current definition updates `owner_id` and the follow-up columns, so dropping them first breaks every account deletion. Copy the current definition from this migration and take out the two `rush_candidates` updates (the playbook's rule: the current definition, not an older file's).
